LESSON 1: WHAT IS SOFTWARE TESTING?
-----------------------------------
Software is made by humans, and humans can make mistakes. Testing is checking that the software works correctly when used the right way, and that it handles wrong input safely.
 
Key terms
- Bug / defect: something that does not work as expected.
- Requirement: a description of what the software should do.
- Test case: a written set of steps with an expected result.
- Expected result: what should happen.
- Actual result: what really happened when the test was run.
- Manual testing: a person runs the tests by hand.
- Automation testing: a script clicks and checks instead of a person.
 
Why automate?
- Scripts finish in hours, while manual testing takes much longer.
- Scripts run the same way every time.
- Scripts can run overnight or on every code change.
 
Why test both positive and negative cases?
- Positive tests check that the system works when used correctly.
- Negative tests check that the system handles mistakes safely.
- Real users make mistakes, and attackers enter bad input on purpose.
 
Bug vs requirement (example)
- Requirement: a user must be able to log in with a valid password.
- Bug: a user enters a valid password and gets an error.

LESSON 2: SDLC AND STLC
-----------------------
SDLC (Software Development Life Cycle) - how software is built, from idea to release:
1. Requirements: gather what the client needs the software to do.
2. Design: plan the screens, flow and database.
3. Development: developers write the code.
4. Testing: testers verify the build.
5. Deployment: the software goes live.
6. Maintenance: fix bugs found after release and add new features.
 
SDLC models (Waterfall and Agile are two examples; others are V-model and Spiral)
- Waterfall: each phase finishes before the next one starts. Testing begins only after development is complete, so problems are found late and cost more to fix.
- Agile: work is split into short sprints (usually 2 weeks). Each sprint delivers a small working piece of the product, and that piece is tested within the same sprint. A regression test (re-checking old features) is also run before release.
 
STLC (Software Testing Life Cycle) - the steps testers follow:
1. Requirement analysis: read and understand the requirements, and find gaps or unclear points.
2. Test planning: decide the scope, tools, schedule (what, how, when).
3. Test case design: write test cases from the requirements.
4. Environment setup: prepare the system to test on.
5. Test execution: run the test cases and record the results.
6. Test closure: prepare the reports and the final status of the test cases.
 
Why is a bug after release more expensive than a bug in the requirements?
- Developers must change the code, and the change must be retested, including old features that might now break (regression).
- The fix must be redeployed to live users.
- Real users may lose data, money or trust in the meantime.
A bug in the requirements is only a sentence corrected in a document.
 
 
LESSON 3: TEST DESIGN TECHNIQUES
--------------------------------
- Equivalence partitioning: divide the inputs into groups that behave the same way, and test one value from each group.
- Boundary value analysis: test just below, on, and just above each edge, because bugs hide at the edges.
- The requirement decides pass or fail, not what the page happens to do.
- Test data should isolate one thing at a time.
 
Practice requirement (made up): a password must be 8 to 15 characters long.
 
Equivalence partitioning
Group      | Length     | Valid?  | Example                     | Expected result
Blank      | 0          | Invalid | (blank)                     | Error: password is required
Too short  | 1 to 7     | Invalid | asdfghj (7)                 | Error: too short
Allowed    | 8 to 15    | Valid   | asdsddddfdf@3e (14)         | Accepted
Too long   | 16 or more | Invalid | wdfjerkjgrtj7ji65yhytrjh (24) | Error: too long
 
Boundary values
Length | Example                   | Valid?  | Reason
7      | abcdefg (7)               | Invalid | One below the minimum
8      | abcdefgh (8)              | Valid   | The minimum
9      | abcdefghi (9)             | Valid   | One above the minimum
14     | abcdefghijklmn (14)       | Valid   | One below the maximum
15     | abcdefghijklmno (15)      | Valid   | The maximum
16     | abcdefghijklmnop (16)     | Invalid | One above the maximum of 15
 
Why these values matter: if a developer wrote "length > 8" when they meant "length >= 8", then 8 would wrongly fail. Only boundary testing catches this.
 
Important: saucedemo has no password length rule. The 8 to 15 rule is made up for practice. The page accepts any length and only checks whether the password matches secret_sauce.

LESSON 4: GIT AND GITHUB
------------------------
Git saves versions of your work (like save points in a game). GitHub stores those versions online.
 
Commands
Command                      | What it does
git init                     | Starts tracking a folder with Git.
git status                   | Shows the state of your files. A new file is "untracked". A changed file is "modified".
git add notes.txt            | Stages the changes in notes.txt, which means choosing what goes into the next save.
git commit -m "message"      | Saves the staged changes as a new version with a short message.
git push                     | Uploads your commits to GitHub.
git diff                     | Shows exactly which lines changed. Run it before git add.
git log                      | Shows each commit with its author, date and message.
git log --oneline            | Shows a short list of commits, one per line.
git branch -M main           | Renames the current branch to main.
git remote add origin <url>  | Tells Git where the online repository lives.
 
The everyday cycle: edit, add, commit, push.
 
Good habits
- Write clear commit messages, such as "Add Lesson 4 Git notes". Avoid "update" or "changes".
- Commit small and often.
- Run git status often.

LESSON 5: GIT BRANCHES
----------------------
A branch is a separate copy of the work where I can make changes without affecting main.
Main is the stable copy and should always work.
Merging copies the finished changes from a branch into main.

Why teams use branches
- Unfinished or broken changes do not affect main.
- Many people can work at the same time without overwriting each other.
- Work is merged into main only after it is finished and reviewed.

Commands
git branch                     - lists branches. The one with * is the current branch.
git checkout -b branch-name    - creates a new branch and moves onto it.
git checkout main              - moves back to main.
git merge branch-name          - brings the branch's changes into the current branch.
git branch -d branch-name      - deletes a branch after it is merged.

Steps
1. Create a branch.
2. Make changes, then git add and git commit.
3. Switch to main.
4. Merge the branch.
5. Push main to GitHub.

Pull request (PR)
A pull request is a request on GitHub to merge a branch into main. A teammate can review the changes first. After the review, the PR is merged.

Fast-forward merge
If main has no new commits while I work on the branch, Git simply moves main forward to the branch's latest commit. No extra merge commit is made.
